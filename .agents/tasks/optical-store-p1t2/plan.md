## Key design decisions (grounded in the code I read)

These are resolved here so the implementer does not re-decide. Rationale is one line each.

1. **Mirror TodoStore's cloud write path exactly.** Every mutation runs inside ONE `db.writeTransaction`, guarded by a `writes = Mutex()` and an `admit(tx, action)` call, and writes three rows: `optical_journal(id,payload,state='queued',ack_revision=0,message='',created_at)`, an overlay row in `optical_drafts(id,body,operation_id)`, and an insert-only `operation_requests(id,payload)` keyed by the `OpticalOperation.id`. This is the proven idempotent op-queue in `TodoStore.save` (lines ~504–553). OpticalStore is cloud-oriented only — there is no `localOnly` optical mode in Task 2 (the optical UI/account wiring is a later task), so DROP the `localOnly` branch entirely and always take the cloud path. Keep the `accountId`, `availableBytes`, `AdmissionPolicy`/`CachePolicy` constructor shape so the later sync task can reuse it; reuse the existing `AdmissionPolicy`/`CachePolicy`/`StorageStats` data classes from TodoStore.kt (do NOT redeclare them).

2. **`optical_drafts.id` keying.** `optical_drafts` has columns `(body, operation_id)` plus the implicit PowerSync `id`. Use `id = customerId` for customer overlay rows and `id = orderId` for order overlay rows. Because customers and orders share one drafts table, prefix order draft ids so the two never collide: store customer drafts under `id = customerId` and order drafts under `id = orderId`, and distinguish them by a `"kind"` discriminator inside the serialized `body` JSON (`{"kind":"customer",...}` / `{"kind":"order",...}`). This keeps a single overlay table (mirrors TodoStore's single `drafts` table) while letting the snapshot read separate the two. Document this in a comment.

3. **JSON body shape in `optical_drafts`.** Store the full serialized domain object as the `body`: `json.encodeToString(customer)` for a customer, `json.encodeToString(order)` for an order (the `OpticalOrder` already embeds its `Customer`, `Prescription`, `FrameDetails`, `LensDetails`, `OrderAmounts` and `payments` list). Use the same `Json { ignoreUnknownKeys = true; encodeDefaults = true }` instance as TodoStore. This is overlay-only state the client reads back; it is NOT the synced-column shape (the synced `optical_orders`/`optical_customers`/`optical_payments` columns are written by the LATER server/sync task from `operation_requests`, exactly as TodoStore's cloud path never writes `server_todos` directly).

4. **Status encoding stays UPPERCASE client-side.** Persist `OrderStatus` via its serializer (UPPERCASE `ACTIVE/READY_FOR_PICKUP/COMPLETE/CANCEL`) inside the serialized order body and in operation payloads, matching `OpticalOperationTest` which round-trips `beforeStatus="ACTIVE"`. Do NOT translate to the backend lowercase enum here and do NOT touch the `@JsonNames` aliases. Add a one-line comment at the status write site noting the later sync task maps UPPERCASE→lowercase (`active/ready_for_pickup/complete/cancel` per migration 017). `OpticalOperation.beforeStatus` carries the uppercase `status.name` (or `"absent"` for creates).

5. **`total_paisa` is never written as an authoritative client value.** `OrderAmounts.totalPaisa` and `OpticalOrder.balancePaisa/paidPaisa` stay computed (they already are). The store serializes the component amounts (frame/lens/extras/discount/tax paisa) and the payment ledger; it never persists a client-authoritative total that could fight the server's generated `total_paisa` column (migration 016 line 80). Any snapshot total is computed in Kotlin from the overlay body, not read from a stored total column.

6. **Customer identity is keyed by `(accountId, normalizedMobile)`.** `order_create` with a new customer upserts the customer and creates the order in the SAME transaction; a known normalized mobile REUSES the existing customer id. Lookup precedence for an existing customer by normalized mobile: first `optical_drafts` customer overlay rows, then synced `optical_customers`. This mirrors how `TodoStore.save` resolves current state (drafts → server_todos → active_todos).

7. **Phone-collision outcome is a typed exception.** Define `class PhoneCollisionException(val existingCustomerId: String, val attemptedCustomerId: String, val normalizedMobile: String) : IllegalStateException(...)` in `OpticalStore.kt`. A `customer_upsert` (or the customer half of `order_create`) throws it when the normalized mobile already belongs to a DIFFERENT existing customer id than the one being written. Callers (UI, later) branch on it. Never silently merge; never silently create a duplicate. (TodoStore surfaces similar guards as `check(...) { "..." }` / `error(...)`; a named exception is the catchable form the task requires.)

8. **Prescription snapshot preservation is structural, not special-cased.** Each `OpticalOrder` already owns its own embedded `prescription`. `customer_upsert` writes ONLY the `optical_customers`/customer-draft row and NEVER rewrites any order body. Editing a customer therefore cannot touch a prior order's prescription — the plan just must not add any cross-write from customer→orders. A test locks this in.

9. **Event bookkeeping rows.** Each state-changing op also inserts an `optical_order_events` row with `event_type` from migration 016's allowed set: `order_create→created`, `order_edit→edited`, `order_status→status_changed`, `payment_add→payment_added`, `payment_refund→payment_refunded`, `image_attach→image_added`, `image_remove→image_removed`. `customer_upsert` has no order and inserts NO event row. The event's `id` = the `OpticalOperation.id` (idempotent — a replayed op's `INSERT` is a no-op via the existing-id guard), `order_id` = the order id, `occurred_at` = op `occurredAt`, `payload` = a small `json_object`-style serialized map (e.g. `{"status":"READY_FOR_PICKUP"}`, `{"paymentId":...,"amountPaisa":...}`, `{"imageId":...}`). These are synced-table rows (`optical_order_events` is a synced table in AppSchema), written in the same transaction.

10. **Idempotent replay.** The idempotency key is `OpticalOperation.id`. Guard every op with `operation_requests` + journal existence like TodoStore: if a row with that `id` already exists in `operation_requests`, the whole op is a no-op (return early inside the transaction). Use `INSERT INTO operation_requests` (insert-only, will also protect against duplicates) and an explicit pre-check so replay is a clean no-op rather than a constraint error. This gives "same OpticalOperation id is a no-op" and "offline create then replay produces no duplicates".

## Operation → transaction shape (the OpticalStore API surface)

Public suspend methods on `class OpticalStore(val db: PowerSyncDatabase, val accountId: String, private val cachePolicy: CachePolicy = CachePolicy(), private val admission: AdmissionPolicy = AdmissionPolicy(), private val availableBytes: () -> Long = { Long.MAX_VALUE })`:

- `suspend fun upsertCustomer(customer: Customer): Customer` — validates via `OpticalRules.validateCustomer`; resolves identity by `(accountId, normalizedMobile)`; throws `PhoneCollisionException` on cross-id collision; writes customer draft + journal + operation_requests (action `customer_upsert`); returns the stored customer (with reused id + bumped revision/updatedAt). No event row.
- `suspend fun createOrder(order: OpticalOrder): OpticalOrder` — validates via `OpticalRules.validate`; in ONE transaction upserts `order.customer` (reusing an existing id by normalized mobile, or using the provided id for a brand-new customer) and creates the order referencing that resolved customer id; writes BOTH customer and order drafts, TWO journal rows OR one combined op — **decision: one `order_create` op whose payload carries the full order (which embeds the customer), plus a separate `customer_upsert` op in the same transaction when the customer is new/changed**, so each op maps 1:1 to an `OpticalPayload` variant and replays independently. Inserts a `created` event. Throws `PhoneCollisionException` if the embedded customer's number collides with a different existing customer.
- `suspend fun editOrder(order: OpticalOrder, before: OpticalOrder): OpticalOrder` — optimistic-concurrency check against `before` (compare current overlay/synced body's revision to `before.revision`, mirroring `TodoStore.save`'s before-check); `OpticalRules.validate`; action `order_edit`; bumps revision; `edited` event. Does NOT rewrite the customer's shared record (edits the order's own body, including its own prescription snapshot).
- `suspend fun changeStatus(orderId: String, next: OrderStatus): OpticalOrder` — loads current order from overlay/synced, applies `OpticalRules.transition` (enforces the allowed matrix + terminal lock + reminder/deliveredAt side effects), action `order_status`, `status_changed` event with `{"status": next.name}` payload.
- `suspend fun addPayment(orderId: String, payment: Payment): OpticalOrder` — appends to the order's `payments` list (do NOT collapse); `require(payment.amountPaisa > 0)`; `require(order.paidPaisa + payment.amountPaisa <= order.amounts.totalPaisa)` ("Payments cannot exceed the order total."); writes updated order draft + an `optical_payments` synced row keyed by `payment.id` + journal `payment_add` op + `payment_added` event.
- `suspend fun refundPayment(orderId: String, payment: Payment): OpticalOrder` — appends a refund entry to the ledger (negative-balance semantics: record the refund as a ledger entry that reduces `paidPaisa`; keep the ledger append-only — do NOT delete the original payment). Decision: represent a refund as a distinct `Payment` row flagged by the `payment_refund` op/event; recompute balance so `balancePaisa` rises. action `payment_refund`, `payment_refunded` event. (Enforce `payment.amountPaisa > 0` for the refund magnitude.)
- `suspend fun attachImage(orderId: String, imageId: String, objectPath: String, contentType: String, byteSize: Long): OpticalOrder` — sets `order.frame.imageKey = imageId` (via `order.copy(frame = order.frame.copy(imageKey = imageId))`), action `image_attach`, `image_added` event with `{"imageId","objectPath","contentType","byteSize"}`. Actual upload pipeline is a later task — bookkeeping only.
- `suspend fun removeImage(orderId: String, imageId: String): OpticalOrder` — clears `frame.imageKey` when it matches, action `image_remove`, `image_removed` event. Bookkeeping only.
- `internal suspend fun snapshot(): OpticalSnapshot` — read helper (decision 11 below).
- `suspend fun recordResult(op: OpticalOperation, accepted: Boolean, ackRevision: Long, message: String)` — mirrors `TodoStore.recordResult`: UPDATE `optical_journal` state to `acked`/`conflict` + ack_revision + message for `op.id`.
- `suspend fun reconcile()` — mirrors `TodoStore.reconcile`: DELETE acked `optical_drafts` whose `operation_id` is an acked journal row at/under the acked revision, then DELETE finished acked journal rows not still referenced by a draft `operation_id`. Keep it minimal (no history_cache/analytics cleanup — optical has none in Task 2).
- `private fun admit(tx, action)` — mirrors `TodoStore.admit`: `check(availableBytes() >= admission.minFreeBytes)`; pending-op cap from `optical_journal` where state in ('queued','conflict'); for order-creating actions, cap active orders against `admission.tasks`. No todo/quarantine/local-only branches.

**Op construction** (all ops): `OpticalOperation(id = UUID.randomUUID().toString(), payload = <variant>, action = <OpticalActions const>, baseRevision = before?.revision ?: 0, previousOperation = <prior draft's operation_id for this entity, or null>, occurredAt = now, beforeStatus = <uppercase status.name or "absent">)`. `payload = json.encodeToString(op)` → written to journal + operation_requests. Use `OpticalActions` constants and the `OpticalPayload` sealed variants verbatim — invent no new models.

11. **`OpticalSnapshot` read helper.** Add `data class OpticalSnapshot(val customers: List<Customer>, val orders: List<OpticalOrder>)` in `OpticalStore.kt`. `snapshot()` runs in `db.readTransaction` under `Dispatchers.Default` (mirror `TodoStore.snapshot`): overlay `optical_drafts` customer/order rows (by `"kind"`) onto synced `optical_customers`/`optical_orders`, draft wins on id collision (`(synced.associateBy{id} + drafts.associateBy{id}).values`), decode bodies with the shared `json`. Orders expose computed `balancePaisa`/`paidPaisa` (already on the model). Keep the customer↔orders relationship by `order.customer.id`. Full-dataset oriented (no pagination) — this is for tests/integration reads, not the UI page path. Because optical synced tables start EMPTY, a queued `order_create` is visible purely from the drafts overlay.

## Test seam note (important, decided here)

TodoStore's DB-backed tests live in **`app/src/androidTest`** as instrumented tests on a real device/emulator, NOT in `app/src/test`. Verified: `src/test` contains only pure-logic JUnit tests (Rules, operations, policies) with zero `PowerSyncDatabase`/`writeTransaction` usage; the store behavior tests (`OfflineStoreTest`, `OrderStatusStoreTest`) are under `androidTest` with `@RunWith(AndroidJUnit4::class)` and build a real `PowerSyncDatabase` via `DatabaseDriverFactory(context)`. PowerSync's SQLite driver needs native libraries + an Android `Context`, so it cannot run under `testDebugUnitTest` (plain JVM), and there is NO existing in-memory/fake PowerSync abstraction in the repo to mirror. The task's "unit tests / `src/test`" guidance explicitly defers to "however TodoStore is unit-tested … mirror that" — and TodoStore's store tests are instrumented. The user has a device connected and approved live testing, so the OpticalStore behavior tests go in `androidTest` and run via `connectedDebugAndroidTest`. `testDebugUnitTest` + `assembleDebug` remain the fast gate for compilation and the existing pure-logic suite (no regressions). Any pure-logic helpers extractable without a DB MAY additionally get a `src/test` test, but the eight required behaviors above need the real DB and belong in `androidTest`.

## Assumptions / gaps noted

- Refund ledger representation: the backend has no "refund" payment method/flag column in migration 016 (`optical_payments.amount_paisa > 0`). Assumption: model a refund as a `payment_refund` **event** plus a ledger entry the client treats as reducing `paidPaisa`, and let the LATER sync task decide the exact backend row shape (e.g. a negative-signed internal entry vs. a reversal record). Task 2 keeps the client ledger append-only and balance correct; it does not finalize the server refund schema. Flag for the sync task.
- `optical_payments` is a synced table but the client does not know the authenticated `user_id`; mirror TodoStore (which also never writes `user_id` into `operation_requests` — the Edge/sync layer injects ownership). Write only the columns the client owns (`order_id, amount_paisa, method, received_at, note, created_at`); leave server-owned columns to the sync task.
